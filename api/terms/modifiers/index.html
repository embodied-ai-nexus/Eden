    Modifiers¶

    Modifiers post-process a term's input or output. Action modifiers sit between an action term and the actuator and model its imperfections (delay, friction, effort clipping, motor strength, backlash, deadband); chain several with Compose. On the observation side, noise models corrupt a term's output during training only, and the observation modifiers in a term's modifiers=[...] list (a moving average, a delay) run in every mode. The actions guide and observations guide show them in context.

    from eden.managers.modifiers.actions.actuators import ActionDelay, Compose
from eden.managers.modifiers.observations.noise import UniformNoise

    ActionModifier(env: EnvBase, options: _TermOptionsT)

    Bases: ConfigurableTermBase[ActionModifierOptions]

    Base class for composable action modifiers.

    Action modifiers intercept and transform processed actions (target positions/velocities) and/or control torques. They are designed to be composed together using :class:~eden.managers.modifiers.actions.actuators.Compose.

    Subclasses override any of three hooks, which run at two different rates:

    • modify_processed_action: once per control step, from the controller's compute(). Its output is processed_action — the command a deployment sends.
    • modify_applied_target: once per physics step (sim_dt), from the controller's apply_actions(), on the command the actuator acts on (e.g. a delay).
    • modify_ctrl_torque: once per physics step, on the torque an explicit controller computed.

    ObservationModifier ¶

    ObservationModifier(env: EnvBase, options: _TermOptionsT)

    Bases: ConfigurableTermBase[ObservationModifierOptions]

    Base class for a transform the observation manager applies to one term's output, frame by frame.

    Listed on an observation term as modifiers=[...]. Each frame of the term goes through its modifiers in list order, then noise, clip and scale, then the group's nan_policy, and last the history window. Unlike noise, a modifier runs in every mode (training, eval, deployment). Each term instance owns its modifier instances, so the same modifier on a policy and a critic copy of a term keeps two independent states.

    compute(frame) is a read, the same rule as for an observation term. The manager calls it every time the observation is computed, which can be several times per control step: from EnvBase.reset(), at phase 19, at phase 12 for the final-observation snapshot, from get_observations(), and once at build to check the output. It returns the output for frame given the modifier's current state and changes nothing.

    advance(frame) is the commit. A stateful modifier (a filter, a delay) folds frame into its state here. The manager calls it right after compute(frame), with the same frame, on the pass that also pushes the history windows (compute(update_history=True)). That pass runs once per control step (phase 19 of RLEnvBase.step, EnvBase.step, each deploy tick) and once per EnvBase.reset(). A partial env.reset(envs_idx) therefore advances every env, the same way it pushes every env's history window. So a modifier's state moves together with the history window, and a delay of k is k pushes. A read that comes after the push and before the next step (get_observations() between steps) applies the current frame once more, as the history window's read does. With backfill, right after a reset, that gives the same value; otherwise it runs one push ahead. A stateless modifier leaves advance as the no-op it is here.

    Two rules keep reads and commits apart:

    • compute returns a tensor it does not write afterwards. The manager uses the output after calling advance, so a view of state that advance updates in place would change under it. Return a fresh tensor, or .clone() the state.
    • Neither method writes into frame, and advance copies what it keeps (self._last.copy_(frame), not self._last = frame). frame may be the raw output that another group's copy of the term also reads (the manager's cross-group cache), the term's own buffer, or a view of simulator state.

    The other hooks: build(frame) allocates the state from a sample frame, before the env steps (allocate here, then write in place: see "Term state lifecycle" in docs/guides/terms.md). reset(envs_idx) restarts the rows of the envs whose episode restarts. It is called with the same indices as the term's history window: None for every env, otherwise an index or boolean-mask tensor to index with.

    A modifier returns a frame of the shape, dtype and device it received. The manager checks this at build, because scale, history and concatenation are all sized from the term's raw output.

    Action modifiers¶

    Composable action modifiers for action terms.

    Action modifiers sit between action terms and the physics engine. They intercept and transform processed actions (target positions/velocities) and/or control torques via composable operations like clipping, delay, friction, and motor strength scaling.

    Modifiers are designed to be composed together using :class:Compose, similar to torchvision.transforms.Compose::

    modifiers = Compose.configure(
    modifiers=[
        ActionDelay.configure(delay_range_steps=(1, 3)),
        FrictionModel.configure(),
        EffortClip.configure(),
    ]

    ActionDelay ¶

    ActionDelay(env: EnvBase, options: ActionModifierOptions)

    Bases: ActionModifier

    Delays the command the actuator acts on by a random number of physics steps, drawn per episode.

    The delay is applied at the actuator, once per physics step (sim_dt), not once per control step: every apply_actions() pushes the controller's command into a history and drives the actuator with the entry d physics steps old. So a latency shorter than a control step can be expressed — at sim_dt=0.005, decimation=4, d=2 keeps the first two physics steps of every control step on the previous command. This matches the physics-step unit of Isaac Lab's DelayedPDActuatorCfg and mjlab's actuator delay_* fields.

    Each env draws d uniformly from the inclusive range when it resets and keeps it until its next reset. The range is given either in physics steps (delay_range_steps) or in seconds (delay_range_s), but not both; with neither, commands pass through. After a reset the history is backfilled with the first new command, so the actuator never acts on a command from before the reset.

    processed_action stays undelayed. It is the command the policy issued, and what a deployment sends. The delay acts only inside apply_actions(), after every modify_processed_action modifier wherever it sits in a :class:Compose chain (which warns when it is listed before one). It models the simulated actuator's latency, and no deployment applies it: eden deploy never calls apply_actions(), so a real robot has only its own latency, and the MuJoCo sim-to-sim robot has none. A policy trained against a delay therefore runs there with less latency than it trained with. With both ends of the range equal, the lag was fixed, so it expects that lag on every step, and a MuJoCo sim-to-sim run does not reproduce it.

    EnvelopeClip(env: EnvBase, options: _TermOptionsT)

    Bases: ActionModifier

    Clips target positions so PD torques stay within the motor torque-speed envelope.

    Back-solves the motor torque-speed curve to find the range of target positions that yield feasible torques, then clips targets into that range. This ensures the PD controller never commands torques outside the motor's physical capability.

    The torque-speed envelope is defined by four parameters::

        Torque, N·m
        ^
Y2──────|
        |──────────────Y1
        |              │\\
        |              │ \\
        |              │  \\
        |              |   \\
--------+--------------|------> velocity, rad/s
                      X1   X2

    Given current joint state (q, dq) and PD gains (kp, kd), the modifier computes the maximum and minimum feasible torques from the T-N curve, then back-solves for the corresponding target position bounds::

    target_low  = (tau_low  + kd * dq) / kp + q
target_high = (tau_high + kd * dq) / kp + q

    By default, T-N curve parameters are read from the entity's actuator spec (dofs_spec). Explicit values override the entity defaults.

    joint_vel = self._entity.get_dofs_vel(dofs_idx_local=self._dofs_idx_local)

    denom = torch.clamp(self._motor_x2 - self._motor_x1, min=CURVE_SPEED_DENOM_MIN)

    # Positive torque limit (tau_high >= 0)
    base_pos = torch.where(
        abs_dq <= MOTOR_STALL_VEL_THRESHOLD,
        self._motor_y2,
        torch.where(joint_vel >= 0.0, self._motor_y1, self._motor_y2),
    )
    tau_high = torch.clamp(base_pos - (base_pos / denom) * over, min=0.0)

    # Negative torque limit (tau_low <= 0)
    base_neg = torch.where(
        abs_dq <= MOTOR_STALL_VEL_THRESHOLD,
        -self._motor_y2,
        torch.where(joint_vel >= 0.0, -self._motor_y2, -self._motor_y1),
    )
    tau_low = torch.clamp(base_neg + (-base_neg / denom) * over, max=0.0)

    # Back-solve: tau = kp * (target - q) - kd * dq
    kd_dq = self._kd * joint_vel
    target_low = (tau_low + kd_dq) / self._kp + joint_pos
    target_high = (tau_high + kd_dq) / self._kp + joint_pos

    ExponentialMovingAverage(env: EnvBase, options: ObservationModifierOptions)

    Bases: ObservationModifier

    Exponential moving average, updated once per control step.

    y(t) = alpha * x(t) + (1 - alpha) * y(t - 1).

    alpha is the weight of the newest frame, as in pandas' ewm(alpha=...). Some filter libraries write the complement, so check that before porting a value. The term's frame must be floating-point — the weights are held in its dtype, so an integer one would truncate them to zero; :class:ObservationDelay is the modifier that carries any dtype.

    A non-finite frame keeps its kind: an infinity entering the average stays an infinity, so a clip on the term still bounds it — a raycast's +inf for "no hit" reaches the policy as the clip's far end, not as a NaN that no clip bounds — and a NaN stays a NaN. Either one stays in the average until the env resets. The group's nan_policy checks the term's output after its modifiers, so it replaces what the policy receives but cannot clean the average itself. The one frame that still averages to NaN is a component that sees both +inf and -inf, their weighted sum being genuinely undefined.

    # first frame since the reset is still to come, ``alpha`` once that frame has been advanced in.
    # ``_hold``, the weight of the stored average, is carried alongside rather than computed as
    # ``1 - _weight`` per read, so the pair is written together everywhere it changes.
    weight_shape = (frame.shape[0],) + (1,) * (frame.dim() - 1)
    self._weight = torch.full(weight_shape, self._first_frame_weight, dtype=frame.dtype, device=frame.device)
    self._hold = torch.full(weight_shape, 1.0 - self._first_frame_weight, dtype=frame.dtype, device=frame.device)

    def compute(self, frame: torch.Tensor) -> torch.Tensor:
    # ``(1 - w) * y + w * x``, written out rather than as ``torch.lerp(y, x, w)``: lerp evaluates
    # ``y + w * (x - y)`` (``x - (x - y) * (1 - w)`` for ``w >= 0.5``), so an infinite frame meets
    # ``inf - inf`` and comes out NaN — which ``clip`` passes through, since ``clamp`` does, and
    # which then reaches the policy. This form turns an infinity into an infinity, so the term's
    # clip still bounds it. Its one indeterminate product, ``(1 - w) * y``, needs ``y`` to be zero
    # wherever ``1 - w`` is; :meth:`advance` is what keeps that true.
    return torch.addcmul(self._hold * self._average, self._weight, frame)

    def advance(self, frame: torch.Tensor) -> None:
    if self.alpha < 1.0:
        self._average.copy_(self.compute(frame))
    # ``alpha == 1`` is pass-through: ``_hold`` is zero everywhere and the average is never read
    # again, so it is left zeroed rather than written. Storing an infinite frame in it would make
    # the next ``(1 - w) * y`` a ``0 * inf``, and so a NaN, for a modifier that changes nothing.
    self._weight.fill_(self.alpha)
    self._hold.fill_(1.0 - self.alpha)

    The delay is counted in pushes of the observation window (see :class:~eden.managers.modifiers.base.ObservationModifier), which happen once per control step. That is the same clock as history_length, so a delayed term with a history window holds the delayed frames.
